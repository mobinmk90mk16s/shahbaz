# ممیزی معماری و نقشه مهاجرت فروشگاه شهباز

> تاریخ ممیزی: 2026-11-13  
> مخزن: `mobinmk90mk16s/shahbaz`  
> شاخه بررسی‌شده: `main`  
> Commit مبنا: `818b1c73043eb16eb52c83c324fc130a2c5ca828`

این سند وضعیت واقعی سورس را ثبت می‌کند تا تغییرات بعدی بر اساس قابلیت‌های موجود انجام شوند، نه بر اساس فرضیات. این سند به‌تنهایی تغییری در Repository ایجاد نکرده است؛ اتصال GitHub فعلی مجوز نوشتن روی شاخه را نداد. هیچ Migration اجرا نشده و هیچ داده یا فایل پروژه حذف نشده است.

## 1. محیط و وضعیت Laravel

- Laravel در `composer.json`: نسخه اصلی `^13.0`.
- حداقل PHP در Composer: `^8.3`. محیط توسعه ثبت‌شده در گفت‌وگو PHP 8.5.12 است.
- Composer 2.x و Vite 7 در پروژه تعریف شده‌اند.
- اتصال توسعه در فایل محلی `.env` روی MySQL تنظیم شده و Migrationهای پایه قبلاً با موفقیت اجرا شده‌اند؛ فایل واقعی `.env` در Repository قرار ندارد.
- فایل `.env.example` هنوز مقدار پیش‌فرض `DB_CONNECTION=sqlite` دارد و با محیط MySQL توسعه هم‌راستا نیست.
- ورودی‌های Vite فعلی فقط `resources/css/app.css` و `resources/js/app.js` هستند؛ رابط فعلی از فایل‌های استاتیک `public/assets` استفاده می‌کند.

## 3. دارایی‌ها و وابستگی‌های JavaScript/CSS

- CSS فعلی: `public/assets/css/style.css` با اندازه حدود 132 KB؛ تمام صفحات از یک فایل مشترک استفاده می‌کنند.
- JavaScript اصلی: `catalog.js`، `app.js`، `storefront-experience.js` و `home-slider.js`.
- `home-slider.js` مخصوص صفحه اصلی است؛ سه فایل دیگر در چند صفحه مشترک‌اند.
- `catalog.js` کاتالوگ نمونه محصولات و دسته‌ها را در `window.SHAHBAZ_CATALOG` و `window.SHAHBAZ_CATEGORIES` قرار می‌دهد.
- `app.js` ساخت Header، Footer، Drawerها و محتوای پویا، عملیات سبد و علاقه‌مندی، صفحه محصول، حساب مهمان و جست‌وجو را مدیریت می‌کند.
- `storefront-experience.js` جست‌وجوی زنده، تجربه فیلتر/مرتب‌سازی، کنترل‌های جزئیات محصول، راهنمای سایز و نوار خرید موبایل را به رابط اضافه می‌کند.
- HTMLهای فعلی از CSS خارجی استفاده می‌کنند؛ در ممیزی نهایی Bladeها نیز باید نبود `<style>` و ویژگی `style=` کنترل شود.
- پوشه `assets` در ریشه Repository با `public/assets` تکرار شده است. نسخه `assets/js/app.js` در ریشه با متن اضافی `php` پیش از کامنت شروع می‌شود، در حالی که نسخه `public/assets/js/app.js` با کامنت معتبر آغاز می‌شود. نسخه Public در زمان اجرای Laravel مرجع فعلی است. هیچ‌یک از دو نسخه در ممیزی حذف نشده‌اند.

## 4. قابلیت‌های واقعی و وضعیت سمت سرور

### موجود در فرانت‌اند

- کاتالوگ ثابت محصولات با شناسه، عنوان، دسته، قیمت، قیمت قبلی، تخفیف، تصویر، توضیح، سایز، رنگ و مشخصه باقی‌مانده.
- صفحه اصلی، چهار صفحه دسته‌بندی، جزئیات محصول، جست‌وجو و نتایج، مرتب‌سازی و اسلایدر.
- افزودن/حذف محصول از سبد، تغییر تعداد، انتخاب سایز و رنگ و نمایش Drawer سبد.
- افزودن/حذف علاقه‌مندی و نمایش Drawer و صفحه علاقه‌مندی‌ها.
- فرم اطلاعات پایه حساب مهمان.
- جست‌وجوی زنده و تعدادی کنترل تعاملی رابط.

### ذخیره‌سازی فعلی مرورگر

کلیدهای اصلی در `public/assets/js/app.js`:

- `shahbaz.cart.v2`
- `shahbaz.wishlist.v2`
- `shahbaz.profile.v1`

کلیدهای Legacy که هنوز خوانده می‌شوند:

- `shahbaz-cart-v1`
- `shahbaz-wishlist-v1`

این ذخیره‌سازی مستقل از حساب کاربری و دستگاه است؛ هنوز API واقعی برای ذخیره حساب، سبد یا علاقه‌مندی وجود ندارد.

### قابلیت‌های هنوز غیرفعال یا پیاده‌سازی‌نشده

- ورود، ثبت‌نام، نشست احراز هویت و تأیید شماره موبایل.
- ارسال واقعی SMS/OTP.
- ثبت سفارش، محاسبه ارسال و پرداخت آنلاین.
- انبار و کنترل موجودی معتبر سمت سرور.
- پنل مدیریت و مجوزهای دسترسی.
- دیتابیس محصولات و دسته‌بندی‌ها.

در نتیجه متن‌های فعلی درباره قیمت، موجودی، ثبت سفارش و پرداخت نباید به‌عنوان اتصال Backend واقعی تلقی شوند.

## 5. وضعیت فعلی Backend و دیتابیس

- `routes/web.php` فقط Route ریشه را به View پیش‌فرض `welcome` متصل می‌کند.
- `resources/views/welcome.blade.php` صفحه پیش‌فرض Laravel است و هنوز صفحه فروشگاه نیست.
- تنها Controller موجود `app/Http/Controllers/Controller.php` پایه Laravel است.
- تنها Model دامنه‌ای، `App\Models\User` پیش‌فرض Laravel است.
- Model فعلی فیلدهای `name`، `email` و `password` را Fillable می‌کند و Hash رمز را Cast می‌کند؛ شماره موبایل ندارد.
- Migration پایه کاربران، ایمیل را اجباری و Unique می‌کند و جدول‌های `password_reset_tokens` و `sessions` را می‌سازد.
- Migrationهای دیگر جدول‌های Cache و Queue را می‌سازند.
- جدول محصول، دسته، Variant، سبد، علاقه‌مندی، سفارش، پرداخت، OTP، نقش و مجوز در حال حاضر وجود ندارد.
- Guard پیش‌فرض `web` از Session و Eloquent User Provider استفاده می‌کند که پایه مناسبی برای Authentication مبتنی بر Session است.
- Seeder پیش‌فرض در صورت اجرا یک کاربر آزمایشی با `test@example.com` می‌سازد؛ این رفتار باید پیش از آماده‌سازی Production بازبینی شود.

## 6. معماری مقصد پیشنهادی

### لایه HTTP

- Routeها بر اساس Storefront، Authentication، Account و در آینده Admin جدا شوند.
- Controllerها فقط درخواست را دریافت، Form Request را اعمال و Service/Action را فراخوانی کنند.
- دسترسی حساب با Middleware استاندارد `auth` محافظت شود؛ صفحات Login/Register با `guest` محدود شوند.
- مقصد بازگشت پس از ورود فقط از مقدار intended معتبر و داخلی پذیرفته شود.

### لایه کاربرد و دامنه

- `app/Services/Auth`: ورود با رمز و جریان OTP.
- `app/Services/Sms`: قرارداد ارسال پیامک و Driver توسعه؛ Driver واقعی فقط با مشخصات سرویس‌دهنده و Secret معتبر فعال شود.
- `app/Services/Cart`: سبد مهمان/کاربر و ادغام تراکنشی پس از ورود.
- `app/Services/Wishlist`: مدیریت علاقه‌مندی‌ها.
- `app/Http/Requests`: اعتبارسنجی مستقل درخواست‌های ورود، ثبت‌نام، OTP و پروفایل.
- `app/Models`: مدل‌های هم‌نام با جداول و روابط Eloquent.
- منطق سفارش و پرداخت تا زمان مشخص شدن الزامات ارسال/درگاه، فعال یا شبیه‌سازی نشود.

### لایه View

- `resources/views/layouts`: Layout فروشگاه و Layout احراز هویت.
- `resources/views/components`: اجزای تکرارشونده مانند Header، Footer، Form Field، Button و Alert.
- `resources/views/pages`: صفحات Home، Category، Product، Cart، Search و Wishlist.
- `resources/views/auth`: Login و Register.
- `resources/views/account`: پروفایل و بخش‌های محافظت‌شده حساب.
- Blade محل منطق تجاری یا CSS نیست؛ فقط داده آماده را نمایش می‌دهد.

### دارایی‌ها

- فایل CSS مشترک فعلی ابتدا بدون تغییر ظاهری به‌عنوان Baseline نگهداری می‌شود.
- سپس CSS بر اساس Base، Components، Layout و صفحات تفکیک می‌شود؛ هر صفحه فقط ورودی CSS لازم خود را بارگذاری می‌کند.
- JavaScript به ماژول‌های مشخص تقسیم می‌شود؛ تا پایان جایگزینی کامل Backend، قراردادهای رفتاری فعلی و selectorها حفظ می‌شوند.
- Vite باید نقطه مدیریت Assetهای جدید باشد؛ فایل‌های استاتیک موجود تا زمان انتقال و تست، حذف نمی‌شوند.

## 7. نقشه داده پیشنهادی بر اساس قابلیت‌های فعلی

### هسته کاربران و امنیت

- `users`: موبایل Unique و اجباری برای حساب‌های جدید؛ ایمیل Nullable/Unique؛ زمان تأیید موبایل؛ وضعیت فعال بودن؛ Hash رمز.
- `otp_challenges`: موبایل، هدف عملیات، Hash کد، انقضا، تعداد تلاش، زمان ارسال، وضعیت و مشخصات نتیجه ارسال؛ بدون نگهداری کد خام.
- `roles`، `permissions`، `role_user` و `permission_role`: RBAC قابل توسعه و مستقل از ورودی کاربر.
- `admin_activity_logs`: ثبت Actor، عملیات، هدف و متادیتای غیرحساس برای اقدامات مدیریتی.
- جدول نشست Laravel حفظ می‌شود؛ نشست‌ها منبع احراز هویت هستند و نه LocalStorage.

### کاتالوگ

- `categories` و `products`: انتقال کاتالوگ hard-coded فعلی به داده سمت سرور.
- `product_images`: در صورتی‌که چند تصویر و ترتیب نمایش محصول تأیید شود.
- `product_variants`: برای ترکیب‌های واقعی سایز/رنگ و موجودی مستقل؛ اگر موجودی هر Variant جداگانه مدیریت نمی‌شود، این جدول تا تعیین قواعد انبارسازی ساده نگه داشته می‌شود.
- کلیدهای متنی/slug باید Unique و فیلدهای پرتکرار مانند category، status و slug ایندکس شوند.

### سبد و علاقه‌مندی

- `carts` و `cart_items`: سبد می‌تواند متعلق به کاربر یا توکن مهمان باشد؛ ترکیب یک محصول و Variant باید یکتا و تعداد محدود شود.
- `wishlist_items`: ارتباط کاربر و محصول با Unique Constraint؛ برای مهمان از شناسه opaque سمت سرور استفاده می‌شود.
- توکن مهمان فقط در Cookie امن HttpOnly قرار می‌گیرد و نسخه Hash‌شده آن در دیتابیس ذخیره می‌شود.
- ادغام سبد و علاقه‌مندی مهمان پس از ورود با Transaction انجام می‌شود و ردیف‌های تکراری به‌صورت کنترل‌شده ادغام می‌شوند.

### ماژول‌های تجاری بعدی

سفارش، آیتم سفارش، آدرس، پرداخت، تخفیف و اعلان تنها پس از تعریف جریان Checkout، سیاست ارسال، وضعیت‌های سفارش و درگاه واقعی طراحی و Migration می‌شوند. وجود دکمه یا پیام نمایشی فعلی به‌تنهایی دلیل کافی برای ساخت جداول ناقص یا شبیه‌سازی پرداخت نیست.

## 8. الزامات Authentication

1. شماره موبایل شناسه اصلی ورود است؛ قبل از ذخیره‌سازی Normalize و سپس Unique می‌شود.
2. ایمیل اختیاری است و در صورت ورود باید معتبر و Unique باشد.
3. رمز عبور فقط با Hash استاندارد Laravel ذخیره می‌شود.
4. ورود با رمز از Guard استاندارد Session استفاده می‌کند و پس از موفقیت Session Regenerate می‌شود.
5. OTP با کد تصادفی امن ساخته، Hash می‌شود و مدت اعتبار و سقف تلاش دارد.
6. درخواست ارسال کد و بررسی کد هر دو Rate Limit دارند؛ OTP تأییدشده مصرف‌شده محسوب می‌شود و دوباره قابل استفاده نیست.
7. برای SMS فقط قرارداد و Driver توسعه/آزمایشی ایجاد می‌شود. هیچ سرویس پیامکی واقعی بدون انتخاب Provider و Secret معتبر فعال معرفی نمی‌شود.
8. حساب غیرفعال اجازه ورود ندارد؛ هیچ فیلد Role یا Admin از Request کاربر پذیرفته نمی‌شود.
9. خروج از حساب Session را Invalidate و CSRF Token را Regenerate می‌کند.
10. Login/Register در Production نباید کد OTP را به Response، HTML یا Log قابل دسترس عمومی افشا کند.

## 9. حفظ داده‌های فعلی زمان مهاجرت

پیش از حذف هرگونه استفاده از LocalStorage، یک Endpoint مهاجرت یک‌باره در نظر گرفته می‌شود که payload قدیمی Cart/Wishlist/Profile را فقط پس از اعتبارسنجی کامل شناسه محصول، Variant و تعداد دریافت می‌کند. این Endpoint باید Idempotent باشد، سبد/علاقه‌مندی مهمان را در دیتابیس بسازد و پس از تأیید ذخیره، داده قدیمی مرورگر پاک شود. از آن پس عملیات دائمی فقط از API سمت سرور انجام خواهد شد.

## 11. مواردی که فعلاً نباید ادعای تکمیل آن‌ها شود

- اتصال SMS واقعی تا زمانی که Provider و تنظیماتش مشخص نشده‌اند.
- پرداخت واقعی تا زمان تعیین درگاه و قرارداد بازگشت/تأیید پرداخت.
- سفارش و انبار تا زمان نهایی شدن گردش سفارش و منبع معتبر موجودی.
- موفقیت تست‌های Browser/Database در محیط توسعه کاربر؛ این موارد باید بعد از دریافت تغییرات در محیط محلی اجرا شوند.

## 12. محافظت از داده و Repository

- تمام Migrationهای جدید افزایشی خواهند بود؛ از `migrate:fresh` استفاده نمی‌شود.
- `.env`، APP_KEY، رمز دیتابیس، API Key و Secret هرگز Commit نمی‌شوند.
- تمام تغییرات روی `main` انجام می‌شوند و شاخه جدید ساخته نمی‌شود.
- فایل‌های HTML و دارایی Legacy تا زمان اثبات برابری رفتاری حذف یا بازنویسی مخرب نمی‌شوند.
